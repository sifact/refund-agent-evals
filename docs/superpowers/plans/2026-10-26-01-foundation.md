# Plan 1 of 5: Foundation (repo, policy, data, refund service) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A public GitHub repo with CI, plus a fully tested refund core: pure policy rules, a frozen/system clock, an in-memory and a Supabase-Postgres repository behind one protocol, row-level security, demo seed data that never expires, and a `RefundService` that is the only way to create or review tickets.

**Architecture:** `policy/` is pure (models, clock, rules). `data/` defines a `RefundRepository` protocol with two implementations and imports only `policy.models`. `service/` orchestrates the repository, the clock and the policy under a per-customer lock, so the running-total check and the ticket write are atomic. No later plan writes tickets any other way.

**Tech Stack:** Python 3.12, uv, pydantic v2, pydantic-settings, psycopg 3, Supabase CLI (local Postgres 54322), typer, pytest, hypothesis, ruff, mypy, pre-commit, gitleaks, and GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-10-26-refund-agent-evals-design.md`

**Roadmap (later plans, each written when the previous one is merged):** 2. Agent + Langfuse tracing · 3. Evaluation suite + CI gate · 4. FastAPI, auth, dark HTML/CSS UI, admin page · 5. Production hardening (Docker, health, rate limits, docs check)

## Review Focus

1. **The same purchase ID requested twice in one request:** it's counted once, and the amount isn't doubled. Test in Task 3: `test_duplicate_requested_ids_counted_once`.
2. **Another customer's real purchase ID:** the reason is `not_owned`, identical to a made-up ID, so the response doesn't reveal that the purchase exists. Test in Task 3: `test_other_customers_purchase_is_not_owned`.
3. **Two concurrent requests for the same purchase:** exactly one ticket is created. The other request sees `already_refunded` (the lock serializes them) or gets `DuplicateRefundError`. Test in Task 6: `test_concurrent_requests_create_one_ticket`.
4. **Reviewing a ticket that isn't `pending_review` (already approved or rejected):** raises `InvalidTicketTransitionError`, and nothing changes. Tests in Task 5 and Task 6.
5. **Timezone at midnight:** `SystemClock` uses `Settings.timezone`, not the machine's local zone. Test in Task 2: `test_system_clock_uses_configured_timezone`.

### Task 3: Refund policy rules

**Files:**
- Create: `src/refund_agent/policy/rules.py` (and export it from `policy/__init__.py`)
- Test: `tests/unit/policy/test_rules.py`

**Interfaces:**
- Consumes: Task 2 models.
- Produces:
  - `PolicySettings(window_days: int, review_threshold_cents: int, running_total_days: int)` (a frozen dataclass), plus the classmethod `PolicySettings.from_settings(s: Settings)`.
  - `decide_refund(purchases: Sequence[Purchase], requested_ids: Sequence[UUID], existing_tickets: Sequence[Ticket], today: date, settings: PolicySettings) -> RefundDecision`

**Algorithm (the tests don't fully pin the order of the checks):**
- Deduplicate `requested_ids`, keeping the first occurrence.
- Check each ID in this order, and the first match wins:
  1. Not in `purchases` (the customer's own): `NOT_OWNED`
  2. On a `REJECTED` ticket: `PREVIOUSLY_REJECTED`
  3. On an `APPROVED`/`PENDING_REVIEW` ticket: `ALREADY_REFUNDED`
  4. `purchased_on > today`: `FUTURE_DATE`
  5. `(today − purchased_on).days > window_days`: `OUTSIDE_WINDOW`
  6. Otherwise eligible.
- `amount` is the sum of the eligible prices. If no item is eligible, `status=None` and `amount=0`.
- Otherwise compute `prior` as the sum of `amount_cents` over approved/pending tickets with `0 <= (today − created_at.date()).days <= running_total_days`. The status is `PENDING_REVIEW` if `prior + amount > review_threshold_cents`, else `APPROVED`.

### Task 6: Supabase schema, RLS, and the Postgres repository

**Files:**
- Create: `supabase/config.toml` (via `supabase init`), `supabase/migrations/20261026000000_init.sql`
- Create: `src/refund_agent/data/postgres.py` (exported as `PostgresRepository`)

**Interfaces:**
- Consumes: the Task 4 protocol and errors.
- Produces: `PostgresRepository(pool: psycopg_pool.ConnectionPool)`. `customer_unit` opens a transaction and runs `SELECT 1 FROM profiles WHERE id = %s FOR UPDATE` (the per-customer lock). A unique violation on `refund_ticket_items_active_purchase_uq` maps to `DuplicateRefundError`. `review_ticket` is one `UPDATE … WHERE id=%s AND status='pending_review' RETURNING *`. When no row comes back, it does a lookup to tell not-found apart from an invalid transition. On reject, the same transaction sets `refund_ticket_items.active = false`.

**Schema (the migration; exact names matter to later plans):**
- `profiles(id uuid primary key references auth.users on delete cascade, display_name text not null, role text not null check (role in ('customer','staff')) default 'customer')`
- `purchases(id uuid primary key default gen_random_uuid(), customer_id uuid not null references profiles, item_name text not null, price_cents integer not null check (price_cents > 0), purchased_on date not null)`, plus an index on `customer_id`
